# 两脸外壳重做：右列从「一个带页签的框」改成「召出的整条」

> 2026-09-20 · 委托方逐屏拍板（八个来回）· 依据：**本机 Claude 桌面端的实测代码**（`app/resources/ion-dist/`，grep 出来的原文）+ 委托方给的五张截图

**状态**：设计稿待委托方过目。**未动任何代码。**
**计划切分**：本稿是**设计**；实施切成三份（§10）。

---

## 1. 为什么要做

计划 3 落地后，右列仍是**一个占宽的列 + 一排页签**（文件 / 预览 / 改动），宽屏下还想劈成两栏。这一夜的全分支终审抓到两条同源缺陷：

- **I4**：split 档下「在右栏审阅 →」是个**死按钮**（面板被边界规则藏掉，点了没有可见反应）。
- **单独立项 · 三列空间预算**：`RAIL_MAX_PX = 360` 而 `TREE_MIN_PX = 200` ⇒ **split 的预览列永远是 ~160px**，两个都不可读。

**根因同一个**：我们想给三样东西各留一条永久列，而 1440–1920 没那么多宽度。

**委托方的判词**（原话）：**「预览、文件树这些就不要共用一个框了，太乱了」**——现状恰恰是把三样挤进一个带页签的框。

## 2. 目标 / 非目标

**目标**
1. 右列**不再是一个常驻的、带页签的宽列**；它是**召出的整条**，一次一只。
2. **两脸各有各的右列内容**（Work = 工作台；Code = 改了什么）。
3. **宽屏时召出的列改成占宽列**（窄屏是浮层）——委托方定。
4. 解掉 I4 与三列预算两条欠账。

**非目标**
- **不**做"搜内容"（`?` 档）——只做名字过滤，占位符按第三态降级（见 §8）。
- **不**接终端（委托方定：**占位不接**）。
- **不**改计划 3 已落地的对话流内件（改动卡、已阅/撤掉/下一个 hunk）。

## 3. 两脸的完整形状（★ 本节是权威）

**两脸共用**：左栏 + 中栏（对话）+ composer。**右列是召出的整条**。

| | **Work 脸** | **Code 脸** |
|---|---|---|
| **头部** | **一个**召出钮（激活时高亮） | **四个键**：命令终端 · Changes · Preview · 更多 |
| **右列内容** | **工作台四段**：`Progress`（可展开）· `Working folder`（文件列表 + 打开方式）· `Scratchpad`（折叠）· `Context`（Connectors + Memory） | **Changes**（分支选择器 + 逐文件 `+N −M`）/ **Preview** |
| **左栏** | **Pinned / Tasks** 两个分组 | **按项目名分组** |
| **输入框上方** | **没有** | `项目名` + `main` + `+N −M` + `Create PR ▾` + `×` |
| **对话流里** | 文件卡（缩略图 + 路径 + 打开方式） | 工具行挂 `+N −M`（可点开）|

**⇒ 一句话**：**Work 脸的右列是"这次任务的工作台"，Code 脸的右列是"这次改了什么"。**
而「改动 / PR」**只出现在 Code 脸**——正合调研 §7.3「**Code 脸恒有 GitHub、Work 脸完全不出现**」。

**★ 我在读图过程中错了三次**（都是委托方纠的），这里记下以免再犯：
1. 把 Code 脸头部的**第 2 个键**读成 "Files 开关" —— 实为 **Changes**。
2. 把**第 1 个键**读成"当前选中的面板" —— 实为 **命令终端**。
3. 把 **Progress** 读成"右侧一栏" —— 实为 **`Work 脸右列里的一段`**（可展开）。

## 4. 四种「召出/收起」的既有范式（不新造轮子）

右列的召出**复用**本仓已有的那套（计划 1–3 建过四回）：把手 + 遮罩 + `Esc` + 角标。**新增一条**：**同一个键开/关**（委托方点名）。

## 5. 浮层 vs 占宽列（委托方定的两档）

| 视口 | 形态 |
|---|---|
| **窄** | **浮层**——浮在对话与 Progress 之上，对话宽度**逐像素不变**，被盖部分变暗 |
| **宽** | **占宽列**——真的一列，从对话拿宽度；**可拖**（委托方定） |

**关闭**：自己的 `×` · `Esc` · 点遮罩 · **再点同一个键**（四条都要通）。
**取不到内容时给一句人话、列不消失**（与计划 3 的卡片同口径）。

## 6. Progress 的归属

委托方原话：**「Progress 就在对话流里，但是只是显示在右侧，不作为独立窗口控制，预览等可以直接挡住 Progress」**
随后又确认：**「Progress 是右列里的一段（可展开）」**。

⇒ 落到实现：**Progress 是 Work 脸右列里的一段**（`Progress ›` + `4 of 4` 这样的计数），**可展开**；
**不是独立控件**、**不参与**任何宽度分配（`railPolicy` 不该知道它）；被浮层盖住时**仍在 DOM 里**，收起后原样回来。

## 7. Code 脸四键的确切构成

| 键 | 图标 | 作用 |
|---|---|---|
| 1 | `>_` | **命令终端** —— **占位不接**（宿主没有交互式终端端点） |
| 2 | `⊞` | **Changes** |
| 3 | `▷` | **Preview** |
| 4 | `⋮` | **更多**：含 **Files**、Background tasks、Open in、Rename、Fork、Transcript view、Output style、Keep computer awake、Archive、Delete |

**★ `Files` 不在那排键里**，在 `⋮` 的菜单里（委托方的图与话都确认过）。
**角标**：蓝点 = 有新内容没看，**沿用** `railVisibility` 已有的 badge 语义。
**菜单里的 Files 点开 → 复用同一个右列**（委托方定）。

## 8. 右列的头与搜索框（照 Claude 的实测代码）

**每一只召出的列的内部结构**（Claude 是 `{header, items}` + 独立一行搜索）：

```
┌────────────────────────────────────────┐
│  <当前内容名> ▾        🔍  ⋮  ⤢  ×     │  头：一行
├────────────────────────────────────────┤
│  [ Filter files…（? 搜内容） ]          │  搜索：独立一行、固定高
├────────────────────────────────────────┤
│  ▸ src                                  │  内容
└────────────────────────────────────────┘
```

**搜索框三态**（**逐字读自 Claude 的 `ion-dist` 代码**）：

| 条件 | 占位符 |
|---|---|
| 内容模式 | `Search files…` |
| 名字模式，内容搜索**可用** | `Filter files… (? for contents)` |
| 名字模式，内容搜索**不可用** | `Filter files…` |

**本稿只做名字过滤**（走已有的 `/api/workspace/files?q=`，就是 `@` 补全那条链）；`?` 那档**不做**，占位符按第三态降级 —— **这正是 Claude 的做法**。

## 9. 对已落地代码的影响

| 现在 | 改成 |
|---|---|
| `railPolicy` 的 `layout: "split" \| "tabbed"` | **取消 `split`**（没有并排两栏了）；改判「浮层 ↔ 占宽列」 |
| `SPLIT_MIN_PX` / `TREE_MIN_PX` / `RAIL_MAX_PX` 三角 | **拆掉**（不再需要"两列各留地板"） |
| `RAIL_PANELS = ["tree","preview","review"]` + 页签行 | **两脸各自的召出面**（Work 1 只 / Code 4 只），**不共用页签** |
| 右栏那只「改动」面板（计划 3 · T7） | **并入 Code 脸的 Changes** |
| `railVisibility` 的 badge | 沿用（挪到召出钮上） |
| 左栏（计划 1） | **加两脸分组差异**（Pinned/Tasks ↔ 项目名） |

**⇒ I4 与三列预算两条欠账在此自然消失**（没有 split 就没有死按钮；没有并排列就没有 160px 的预览列）。

## 10. 计划切分（委托方定 · **已按勘查结果重切过一次**）

| 计划 | 内容 | 为什么这么切 |
|---|---|---|
| **4** | **右列骨架**（两脸的召出钮就位、拆 split、拆页签行、浮层↔占宽列、四条关闭路径、同键开/关）+ **它失效的测试锁与探针的更新** | 骨架是后面几步的地基 |
| **5** | **左栏两脸分组**（Work = Pinned / Tasks；Code = 项目名） | **勘查后拆出来的**：`Pinned` / `Tasks` 在仓里**不存在**，是一个**新概念**（置顶标记：存哪、怎么置顶、跟不跟项目走），与右列骨架不是一个量级；且左栏**已有一条负向锁挡在路上**（`test/ui-file-tree.test.ts:292` 禁止 `.sidebar[data-workspace-face="code"] .run-list`） |
| **6** | **Work 脸右列的工作台四段**（Progress / Working folder / Scratchpad / Context） | 四样**全是新的面**，与骨架解耦 |
| **7** | **Code 脸的 Changes/Preview + 输入框上方那条 + Files 搜索框** | 依赖骨架；Changes 要在计划 3 那只「改动」面板的成果上改 |

**★ 重切的原因（如实记）**：委托方最初定的是「左栏并进 4」，但那是在**勘查之前**——三条勘查回来后才知道 ① 左栏那半是新概念不是改造 ② 计划 4 的破坏面是 **~22 条测试锁 + ~10 个失效探针**。把这两件事摆给委托方之后，改成了左栏拆出去。

**★ 计划 4 里 Work 脸的权宜**：骨架先就位，**Work 脸那一个钮暂时挂现有的树/预览**（计划 6 再换成工作台四段）。**这是刻意的、写在计划里的中间态**，不是遗漏。

**★ 与「不许改已有探针」那条约束的冲突及裁定**：计划 2/3 定的是「不许改 `_audit-20260919/` 里已有的报告与探针」。计划 4 **必然让其中 ~10 个失效**（它们依赖 tab 行、split 档、`--rail-tree-w` 这些即将不存在的东西）。**裁定：允许计划 4 更新它失效的那些探针，并把"哪个探针为什么改"逐条记进计划；旧报告一个字不动**。理由：那些探针是**针对某个已过去状态的验收记录**（一次性、打活页），不是回归测试。

## 12. 验收怎么算过了

- **两脸各自的右列能召出/收起**，且**同一时刻只有一只**。
- **窄屏下召出前后，对话宽度逐像素不变**（这是"浮层"与"占宽列"的分界）。
- **宽屏下召出的是真的一列**，且**可拖**。
- **Progress 在 Work 脸右列里、可展开**；被盖住时仍在 DOM 里、收起后原样回来。
- **Code 脸四键**各自召出对应的列；**`Files` 在 `⋮` 菜单里**。
- **左栏两脸分组不同**，且**差异只收在 `body[data-face]` 上**（计划 1 的规矩：两脸差异只许收在那一个属性上，**且必须成对**）。
- **搜索框按三态显示占位符**（本稿只实现第一/第三态）。
- **四条关闭路径都通**（`×` / `Esc` / 遮罩 / 同键）。
- 一条**能红的探针**：删掉"一次一只"那条约束，看它红不红。
